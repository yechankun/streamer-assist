## 처리 경로 추가 최적화 — 2026-10-08

`84aa93f`의 처리 코드와 비교했습니다. 오래된 중복 ID·프로필을 찾는 반복 탐색을 FIFO 링 큐로 바꾸고, 하이라이트 대기 구간의 계산과 불필요한 증거 배열 생성을 제거했습니다. 키워드·반복 문구 순위는 필요한 상위 항목만 유지하며 동률의 기존 순서를 보존합니다. 미저장 이벤트 수는 수용·확정 시 갱신하고, 스크롤 기록의 중복 ID 집합도 이어 사용합니다. 큰 반응 버퍼는 채팅이 완전히 끊기지 않아도 사용량이 줄면 축소합니다.

Ryzen 7 3700X·Node.js 22.22.2에서 같은 입력의 결과 해시를 확인한 3회 교차 실행 중앙값입니다. 이 표는 **디스크·SQLite·플랫폼 네트워크·화면을 제외한 계산 비용**입니다.

| 작업 | 이전 | 개선 후 |
| --- | ---: | ---: |
| 채팅 100,000건, 참여자 1,000명 | 2,862ms | 937ms |
| 채팅 100,000건, 모두 다른 참여자 | 3,567ms | 1,055ms |
| 키워드·반복 문구 각 10,000개, 순위 100회 | 563ms | 31ms |

폭주 뒤 최근 40건을 유지한 회귀 조건에서는 반응 버퍼의 용량이 65,536칸에서 1,024칸으로 줄었고 시간창·참여자·반응 집계와 재확장을 확인했습니다. 이는 해당 버퍼의 축소이며 앱 전체 RAM 감소율이 아닙니다.

실제 Electron·화면·투표·추첨·암호화 저장을 포함한 추가 5초 시험에서 2만/초 요청은 100,000건, 새 참여자 1만/초 요청은 50,000건의 원본·고유 참여자·표를 정확히 유지하고 종료 시 대기·재시도·누락 집계가 0이었습니다. 송신자는 요청 속도보다 느립니다. 저장 완료 대기는 실행마다 달랐으며 계산의 개선 배율을 전체 기록 처리량의 개선으로 해석하지 않습니다. 독립 사본에서 화면 빌드가 빠진 측정은 비교에서 제외했습니다. 측정 도구는 빌드와 화면 준비를 확인한 뒤 시작합니다.

재현: `node scripts/benchmark-processing.cjs --baseline-revision 84aa93f`. 로컬 결과는 `release/processing-performance.json`과 `release/optimization-{before,after}-{live,distinct}.json`, 새 참여자 재측정의 `-repeat.json` 파일에 있습니다. 합성 조건과 PC·디스크·메시지·참여자 구성에 따라 달라지며 플랫폼 전체 메시지 전달의 보장값은 아닙니다.

다시보기 모드의 50만 건은 원문을 쓰지 않고 실시간 투표·모집에 처리한 결과이며 원본 수집 보장 시험은 아닙니다. 원본 저장 시험은 마지막 대기열·재시도·집계된 누락이 모두 0이었습니다. 부하 상태 전용 커밋량은 약 338~657MiB로 유휴 RAM과 다릅니다. 참여자가 많거나 기록이 늘면 메모리가 증가합니다. 별도 회귀 검사는 62,000명 정확한 집계, 캐시에서 빠진 ID의 재전송, 디스크 장애, 워커 준비 전후 재시작, 종료한 방송의 임시 기록 복구, 여러 영상의 시간순 하이라이트를 확인합니다.

개선 전 5만/초 과부하 시험은 수신 50만 건 중 78,129건만 저장했고 메인 루프 최대 지연은 15.46초였습니다. 개선 후 수용한 부하를 임시 기록으로 보존하고 처리 중 양보하지만 **103.8초 대기는 해당 저장 부하로 5만/초를 무한히 지속 처리할 수 없다는 증거**입니다. 저장 대기가 커지면 투표·모집 처리도 늦어질 수 있습니다. 2만/초는 30초 시험이며 매번 새 참여자가 등장한 1만/초 시험도 최대 659ms 지연이 있습니다. 무제한 부하에서 일정 메모리·속도나 플랫폼이 보내지 않은 메시지 복구를 보장하지 않습니다. 갑작스러운 종료는 영구 저장 전 휘발 구간을 잃을 수 있으며 지속적인 저장 장애는 조치가 필요합니다.

## 유휴·트레이 동작 — 2026-10-08

Windows x64·논리 프로세서 16개에서 실제 화면 번들, Electron 41.10.7·내장 Node.js 24.18.0으로 비교했습니다. 이전 기준은 `5ba36f0`입니다. 상태별 2초 준비 후 15초를 측정했습니다. 두 버전 모두 빈 새 프로필이며 실제 방송·AI 구성요소·개인 인증 정보·강제 GC를 사용하지 않았습니다. AI 상태는 설정 → AI 화면을 연 뒤 트레이로 숨겨 비교했습니다. 실제 창 검사와 측정은 순차 실행했습니다.

| 상태 | CPU 이전 → 개선 후 | 전용 커밋량 이전 → 개선 후 |
| --- | ---: | ---: |
| 홈 표시 | 0.141% → 0.188% | 227.9 → 220.0 MiB |
| 홈 최소화 | 0.045% → 0.043% | 227.8 → 218.7 MiB |
| 홈 트레이 | 0.038% → 0.036% | 228.5 → 214.9 MiB |
| AI 설정 표시 | 0.199% → 0.131% | 229.2 → 228.2 MiB |
| AI 설정 트레이 | 0.118% → 0.028% | 222.2 → 219.9 MiB |

CPU는 앱 프로세스들의 누적 CPU 시간 차이를 합쳐 논리 프로세서 수로 나눈 값입니다. 메모리는 앱 프로세스의 private bytes 합계를 MiB로 표시합니다. working set 합계는 공유 페이지를 중복 계산할 수 있습니다. 짧은 유휴 CPU 측정은 변동이 있으며 이번 표시 상태의 CPU는 JavaScript 작업 감소에도 증가했습니다. 모든 PC의 보장 값이나 방송 연결 상태의 측정은 아닙니다.

### 커밋량과 실제 상주 RAM의 차이

위 표는 **전용 커밋량**이며 작업 관리자의 전용 상주 메모리와 다릅니다. 커밋량은 RAM·페이지 파일로 뒷받침하는 메모리 약정이고, 전용 상주 메모리는 현재 RAM에 있는 전용 페이지입니다. 공유 상주 페이지도 메모리를 사용하지만 각 프로세스에 별도 사본이 있는 것처럼 중복 합산하면 안 됩니다. [Microsoft의 메모리 지표 설명](https://blogs.windows.com/msedgedev/2021/01/13/investigate-microsoft-edge-memory-usage/)을 참고하세요.

2026-10-08의 별도 빈 프로필 실험에서 앱 홈 화면을 숨긴 상태는 **전용 상주 92.4MiB / 전용 커밋 220.4MiB**였습니다. 격리 프로필에서 모든 창을 해제한 실험은 **전용 상주 71.8MiB / 전용 커밋 191.3MiB**였으며 전역 단축키 등록도 유지됐습니다. 이는 가능성 확인 실험으로, **정식 트레이 동작에 적용했거나 화면 복귀까지 검증한 결과는 아닙니다**. 배포 앱은 창·입력을 유지하며 숨깁니다. 창 없는 빈 Electron은 이 PC에서 **전용 상주 45.2MiB / 전용 커밋 103.7MiB**였습니다. 강제 작업 집합 비우기·GC·개인 프로필·실제 방송 연결은 사용하지 않았습니다.

유휴 측정 도구에 Windows 카운터의 `privateResidentMiB`와 프로세스별 커밋·상주 합계를 추가했습니다. 상주 카운터는 CPU 측정 후 별도로 조회한 마지막 시점의 값이며 위 표의 평균과 다릅니다. 지원하지 않거나 조회할 수 없으면 `null`로 표시합니다. 100MiB 미만 목표는 사용할 메모리 기준도 정해야 합니다. 화면 해제는 렌더러 메모리를 줄이며 정식 트레이 절전에는 입력·창·대화상자·진행 작업의 복원 검증이 추가로 필요합니다.

이전 버전은 상태마다 엔진 스냅샷을 15회 만들었으며 숨김·최소화에서도 생성했습니다. AI 상태에서는 조회도 각각 10회 발생했습니다. 개선 후 빈 프로필의 측정 구간에서는 두 작업 모두 발생하지 않았습니다. AI를 추가했다면 표시 중인 설정은 10초 상태 조회를 유지하고 트레이에서는 해당 UI 조회를 중단합니다.

최초 JavaScript는 **427.53 → 334.45kB(21.8% 감소)**, 최초 CSS는 **128.76 → 79.42kB(38.3% 감소)**입니다. 타임라인·AI 번들은 패키지에 모두 포함하고 필요할 때 로드합니다. 기능을 제거한 결과가 아니며 설치 파일도 같은 비율로 줄었다는 의미는 아닙니다.

백그라운드 검사는 실제 수집 콜백과 로컬 네트워크 대체물을 사용해 **채팅 2,001건·후원 10건**, 중복 제외·정확한 저장 순서·실제 Windows 전역 마커 단축키·투표 자동 마감·숨긴 화면의 스냅샷 미생성·표시/복귀 시 최신 상태를 확인합니다. 수집·연결 유지와 재접속·방송 감지는 앱에서 계속 수행합니다. 기록 중 1초 저장과 메타데이터 5초 저장 주기를 유지하고 연속 채팅에서 저장 시점 유지와 실패 재시도도 단위 검사합니다. AI 인증·분석 작업은 앱에서 진행하며 트레이 최적화는 UI 작업을 줄입니다.

## 합성 기록 측정

24일·채팅 24,000건의 암호화 파일은 **741,456 → 566,024바이트(23.7% 감소)**였습니다. 첫 날짜 조회는 **91개 → 1개** 청크를 읽었고 5회 중앙값은 **80.81 → 0.90ms**였습니다.

저속 기록 예시에서 1초 저장 120회를 수행한 결과 **120개 파일·46,268바이트 → 1개·2,032바이트**였습니다. 1초 저장 주기를 유지하고 같은 날짜의 제한된 마지막 파일을 원자적으로 합칩니다.

AES-GCM 테스트 저장소를 사용하므로 Windows DPAPI 실제 시간과는 다릅니다. 디스크·운영체제 캐시·채팅 패턴·기록 크기에 따라 결과가 달라집니다. 개인 프로필이나 실제 채팅을 측정하지 않았습니다.

## 재현

- `npm run benchmark:timeline`은 임시 합성 데이터를 만들고 정리합니다. 새 체크아웃은 현재 결과를 출력하며 이전 비교에는 로컬로 보관한 이전 코드가 필요합니다.
- `npm run benchmark:idle`은 검증된 화면을 빌드하고 빈 임시 프로필을 측정합니다. `node scripts/benchmark-idle.cjs --sample-ms 15000 --output release/idle-performance-optimized.json`으로 위 측정 구간을 재현합니다. `--root <이전 체크아웃>`은 별도로 빌드한 이전 버전을 동일한 도구로 측정합니다. 보고서는 CPU·private memory 합계, 화면 힙·스크립트 시간, 스냅샷·IPC 횟수를 담고 개발 프로필은 사용하지 않습니다. 로컬 비교 파일은 `release/idle-performance-baseline.json`·`release/idle-performance-optimized.json`입니다.
- `npm run build`는 `release/renderer-build-timings.json`을 기록합니다. 새 번들은 `node scripts/build.cjs --force`, 증분 타입 상태 초기화는 `.build-cache/typescript.tsbuildinfo`만 제거합니다.
- `npm run test:desktop`은 `release/desktop-test-results.json`에 검사별 시간을 남깁니다. 선택 실행은 별도 보고서를 사용합니다.
- `npm run dist:all`은 `release/build-timings.json`을 기록합니다. 겹쳐 실행되는 단계 시간을 더한 값은 전체 시간과 다릅니다.
- 로컬 비교 보고서는 `release/build-performance-report.json`·`release/test-performance-report.json`입니다. 생성 결과는 Git에서 제외합니다.

캐시 검사는 수정 시각을 유지한 편집, 결과 변조·누락, 환경·가져온 파일 변화와 네이티브 의존성 추가를 확인합니다. 실제 TypeScript 오류를 넣어 게시 실패·이전 결과 보존·오래된 소스의 패키징 차단도 확인했습니다.
